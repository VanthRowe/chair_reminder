# 提交 Git

当用户说"提交git"时，根据当前对话记录梳理本次修改内容，生成并执行 `git commit`。

## 触发条件

用户输入包含"提交git"或含义相同的表达。

## 执行步骤

1. 先执行 `git status`（必要时 `git diff`）查看仓库实际改动，与对话记录对照，确定本次提交范围。
2. **提交门禁**：确认本次改动的 Keil 编译已在本次会话内跑过且 `0 Error(s)`（已执行过的结果有效，不重复跑）；未跑过的先执行编译命令（见 AGENTS.md 常用命令），不通过禁止提交。纯文档/配置改动可跳过编译。
3. 在当前对话记录中查找本次修改的相关内容：
   - 修改了哪些文件；
   - 新增、修复或更新了什么功能或逻辑。
4. 判断修改类型：
   - 新增功能 → `<feature>`；
   - bug 修复 → `<bugfix>`；
   - 不属于上述两类（如配置调整、代码重构、文档更新等） → `<update>`。
5. 按以下格式生成 commit 信息：
   - feature / update 类型：`<修改类型><修改内容>`；
   - bugfix 类型：`<修改类型><修改内容><修改原因>`，其中修改原因需从对话记录中分析得出。
6. 用 `git add <相关文件>` 只暂存与本次修改相关的文件（禁止 `git add -A` / `git add .`，避免把构建产物等无关文件一并提交），然后执行 `git commit -m "<生成的信息>"`。是否 `git push` 由用户另行明确指示，默认不推。
7. 提交后简要汇报：commit 哈希、提交信息、包含的文件。

## 示例

- 新增功能：`<feature><添加 log 日志组件>`
- bug 修复：`<bugfix><修复 PWM 占空比跳变><因通道配置时未先关闭输出>`
- 其他更新：`<update><整理工程文件分组>`

## 注意事项

- 提交信息只写最终交付的变更内容，不写开发过程中的任何问题——中间 bug、AI 能力缺陷导致的返工、过程中的任何缺陷，都不写（与最终交付无关，看历史的人只关心改了什么，不关心改的过程）。
- 若对话记录中没有足够信息，应询问用户本次修改概要。
- 执行 git commit 前需确认用户已在仓库中完成改动。
